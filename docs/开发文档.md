# PhishGuard 钓鱼邮件智能检测与防范系统 · 开发文档

> 版本：v0.1（MVP 设计稿）　日期：2026-11-12　状态：待评审
> 定位：面向国内中小企业的钓鱼邮件检测 SaaS，同时作为毕业设计《基于 NLP 与机器学习的钓鱼邮件智能检测与防范系统研究》的实现载体。
> 产品名 PhishGuard 为暂定名。

---

## 1. 项目概述

### 1.1 背景
钓鱼邮件是企业遭受财务诈骗、账号失窃、勒索软件的主要入口。大厂的邮件安全产品（Coremail 安全网关、奇安信、深信服等）主要服务中大型政企，几十人规模的中小企业基本无人覆盖，而这类企业恰恰是"冒充老板转账""冒充供应商改收款账户"的重灾区。

### 1.2 产品目标
1. **接入简单**：填写邮箱地址加授权码，5 分钟内开始防护，不改 MX 记录、不装客户端。
2. **检测可信**：规则引擎加 NLP 模型双层检测，每个判定都给出可读的理由。
3. **处置闭环**：高风险邮件自动隔离，中风险邮件标记提醒，管理员复核，误报和漏报反馈回流训练。
4. **可私有化**：全部组件 Docker 化，同一套代码既能跑 SaaS，也能交付私有化部署。

### 1.3 MVP 范围

| 包含 | 不包含（后续版本） |
|---|---|
| IMAP 通用接入（腾讯/阿里/网易企业邮、Coremail、Outlook 等） | M365 Graph API、Gmail API 接入 |
| 邮件解析：邮件头、正文、URL、附件元数据 | 附件沙箱动态分析、二维码识别 |
| 规则引擎、TF-IDF 基线模型、DistilBERT 模型、融合打分 | 大模型在线研判（作为可选插件预留接口） |
| 自动隔离、可疑标记、人工放行和删除 | 投递前拦截（SMTP 网关模式） |
| Web 工作台：总览、邮件、隔离区、邮箱接入、手动检测、白名单 | Outlook / 浏览器插件的员工一键上报 |
| 单租户多管理员、审计日志 | 多租户计费、SSO |
| Docker Compose 一键部署 | Kubernetes、高可用集群 |

### 1.4 用户角色
- **管理员（admin）**：配置邮箱接入、白名单、阈值，管理用户。
- **安全运营（operator）**：查看告警、复核隔离区、提交反馈。
- **只读（viewer）**：查看报表。

```
                    │ api (FastAPI)                                │
                    │  认证 / 邮件查询 / 隔离处置 / 配置 / 手动检测    │

                │ 业务数据      │ │ 任务队列    │ │ 解析+规则+模型+融合 │
                └───────▲──────┘ └─────▲──────┘ └─────▲─────────────┘
                        │              │              │

                    │ worker (Celery)                              │
                    │  ├─ imap_sync：按邮箱轮询/IDLE 拉取新邮件        │
                    │  ├─ detect：调用 detector 打分                 │
                    │  └─ action：IMAP MOVE 隔离 / 打标 / 告警推送     │
                    └──────────────────────┬───────────────────────┘
                                           │ IMAP over TLS (993)
                                  ┌────────▼────────┐
                                  │ 客户企业邮箱服务器 │
                                  └─────────────────┘
```

**核心设计决定**
- **detector 是一个独立 Python 包**，api（手动检测）和 worker（自动检测）共同引用，保证两条路径的判定结果一致；毕设实验脚本也直接调用它。
- **模型推理在 worker 进程内完成**（ONNX Runtime，CPU），MVP 不单独拆推理服务；当吞吐成为瓶颈时再拆出 `inference` 服务。
- **邮件原文不长期保存**：只保存结构化元数据、检测结果和截断后的正文摘要；原始 .eml 仅对被隔离邮件保存，带保留期（默认 30 天）。

## 3. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 后端框架 | Python 3.11 + FastAPI | 与机器学习生态同语言；异步、自带 OpenAPI 文档 |
| ORM / 迁移 | SQLAlchemy 2.0 + Alembic | 成熟、迁移可控 |
| 任务队列 | Celery 5 + Redis 7 | 定时同步、检测任务异步化、重试 |
| 数据库 | PostgreSQL 16 | JSONB 存检测明细；全文检索可用 |
| 邮件 | `imapclient`、标准库 `email` | IMAP IDLE / MOVE 支持完善 |
| NLP / ML | scikit-learn、Hugging Face Transformers、PyTorch（训练）、ONNX Runtime（推理） | 训练用 PyTorch，线上用 ONNX 减小镜像、提升 CPU 推理速度 |
| 可解释性 | SHAP（基线模型）、注意力 / 词重要度（Transformer） | 给出可疑词高亮 |
| 前端 | Vue 3 + Vite + TypeScript + Element Plus + ECharts + Pinia | 国内生态成熟，组件齐全 |
| 部署 | Docker + Docker Compose，Nginx | 一键部署，私有化交付友好 |
| 加密 | `cryptography` Fernet（凭证）、bcrypt（密码）、JWT | 授权码必须可逆加密存储 |

## 5. 功能模块设计

### 5.1 邮箱接入（Mailboxes）
- 管理员填写：邮箱地址、IMAP 主机和端口（内置常见服务商预设）、授权码、要监控的文件夹（默认 INBOX）。
- 保存前执行**连接测试**：登录、`SELECT INBOX`、检查服务器是否支持 `MOVE` / `IDLE` 能力，结果回显。
- 授权码使用 Fernet 加密存储，密钥来自环境变量 `CREDENTIAL_KEY`，任何接口都不返回明文。
- 首次接入时**只记录当前最大 UID，不回扫历史邮件**（可选回扫最近 N 天，默认关闭）。
- 自动在邮箱中创建隔离文件夹 `PhishGuard-隔离`（名称可配置）。
- 状态：`active` / `paused` / `error`（附最近一次错误信息），连续失败 5 次自动暂停并告警。

**常见服务商预设**

| 服务商 | IMAP 主机 | 端口 |
|---|---|---|
| 腾讯企业邮 | imap.exmail.qq.com | 993 |
| 阿里企业邮 | imap.qiye.aliyun.com | 993 |
| 网易企业邮 | imap.qiye.163.com | 993 |
| Outlook / M365 | outlook.office365.com | 993 |

> 注：M365 已逐步停用 IMAP 基本认证，Outlook 预设仅适用于仍允许基本认证的租户；正式支持放到 Graph API 版本。上线前逐一实测各服务商的 MOVE/IDLE 支持情况。

### 5.2 邮件同步（worker: imap_sync）
1. Celery beat 每 60 秒为每个 `active` 邮箱派发一次同步任务（支持 IDLE 的邮箱改为长连接，MVP 先用轮询）。
2. 用 `UID SEARCH UID {last_uid+1}:*` 拉取新邮件，`FETCH (UID RFC822.SIZE BODY.PEEK[])`，**使用 PEEK 不改变已读状态**。
3. 超过 `MAX_EMAIL_SIZE`（默认 25MB）的邮件只取邮件头和正文，跳过附件内容。
4. 每封邮件写入 `emails` 表（状态 `pending`）后投递 `detect` 任务；用 `(mailbox_id, uid_validity, uid)` 唯一约束保证幂等。
5. 若服务器 `UIDVALIDITY` 变化，重置游标并记录审计事件。

### 5.3 检测引擎（detector）
见第 7 章。

### 5.4 处置（worker: action）

| 判定 | 风险分 | 默认动作 |
|---|---|---|
| `phishing` 钓鱼 | ≥ 80 | IMAP MOVE 到隔离文件夹；保存原始 .eml；推送告警 |
| `suspicious` 可疑 | 50–79 | 保留在收件箱，打 IMAP 关键字标记 `$PhishGuard_Suspicious`（服务器支持时）；在工作台待复核列表出现 |
| `safe` 安全 | < 50 | 不处理 |

- 阈值在设置页可调，并支持"仅检测不处置"的观察模式（新客户默认开启 7 天，用来观察误报）。
- **放行**：把邮件从隔离文件夹 MOVE 回原文件夹，自动生成一条"误报"反馈。
- **删除**：在隔离文件夹中标记 `\Deleted` 并 EXPUNGE，需二次确认，写审计日志。
- **告警推送**：企业微信群机器人和钉钉机器人 Webhook，MVP 至少实现其中一个；邮件告警作为备选。

> IMAP 方案的限制：邮件投递后才处理，存在数秒到一分钟的暴露窗口；无法修改已投递邮件的内容（不能插警告横幅）。产品文案中不得宣传为"拦截"，统一称"检测与自动隔离"。

### 5.5 手动检测
- 支持上传 `.eml` 文件或粘贴邮件原文 / 正文文本。
- 同步调用 detector，返回完整检测报告，**不入库**（除非用户选择"保存到样本库"）。
- 用于毕设演示和安全人员研判可疑邮件。

### 5.6 白名单（Allowlist）
- 类型：发件人邮箱、发件域名、URL 域名。
- 白名单**只用于降低规则分，不跳过认证检查**：SPF/DKIM 失败的"白名单发件人"仍然告警（防止被仿冒）。
- 每条白名单记录创建人、原因和可选的过期时间。

### 5.7 反馈闭环
- 运营人员可对任意邮件标注：`确认钓鱼` / `误报` / `漏报`。
- 反馈写入 `feedback` 表，`ml/scripts/prepare_data.py` 可导出为训练集增量。
- 管理后台展示近 30 天误报率、漏报数，作为模型效果的线上指标。

### 5.8 工作台页面

| 页面 | 核心内容 |
|---|---|
| 登录 | 账号密码；登录失败 5 次锁定 15 分钟 |
| 总览 | 今日检测数 / 隔离数 / 待复核数 / 误报率；近 30 天检测趋势（折线）；判定分布；高频攻击类型（横向条形图）；最近高风险邮件列表 |
| 邮件列表 | 筛选（判定、邮箱、时间、发件人、关键字）；表格列：时间、发件人、主题、所属邮箱、风险分、判定、状态；分页 |
| 邮件详情 | 风险分仪表；命中规则列表（含权重）；模型分数；可疑词高亮的正文；URL 列表（真实链接与显示文本对比）；邮件头认证结果；操作：放行 / 删除 / 反馈 |
| 隔离区 | 被隔离邮件列表，批量放行 / 删除，显示剩余保留天数 |
| 邮箱接入 | 邮箱列表与状态；新增（服务商预设 + 连接测试）；暂停 / 恢复 / 删除 |
| 手动检测 | 上传 / 粘贴 → 检测报告（复用详情页组件） |
| 白名单 | 增删改查，显示命中次数 |
| 设置 | 阈值、观察模式、告警 Webhook、数据保留期、用户管理、审计日志 |

**视觉方向（待确认）**：产品型界面，以信息清晰和密度优先，不做营销页式的大字和动效。浅色主背景加深色侧边栏；主色避开"安全产品一律蓝色"的惯例，暂定青绿色（teal），与红色"钓鱼"、琥珀色"可疑"、绿色"安全"三种语义色明确区分；卡片使用细描边和极轻阴影，数字等宽对齐。开发前出一版总览页和详情页的高保真稿确认后再铺开。

## 7. 检测引擎详细设计

### 7.1 处理流程

```
原始邮件字节
  → parser：解码 MIME，提取 headers / text / html→text / urls / attachments
  → allowlist 预检（只影响加分，不跳过认证检查）
  → rules：逐条执行，输出命中列表与规则分 R（0–100）
  → models：baseline 概率 Pb，transformer 概率 Pt
  → fusion：融合得到最终风险分 S 与判定
  → explain：生成理由（命中规则 + 可疑词 + 一句话总结）
```

### 7.2 特征清单

| 类别 | 特征 |
|---|---|
| 邮件头 | SPF / DKIM / DMARC 结果（解析 `Authentication-Results`）；From 与 Reply-To 域名不一致；From 显示名包含邮箱地址或高管姓名；Return-Path 与 From 不一致；Received 跳数；X-Mailer 异常 |
| 发件域 | 与常见品牌或客户自有域名相似（编辑距离、同形字 / punycode）；免费邮箱冒充企业 |
| URL | IP 直连；punycode；短链接；子域层级过深；URL 长度；含 `@`；显示文本域名与真实 href 域名不一致；可疑顶级域；非 HTTPS 登录页关键词 |
| 正文（中英） | 紧迫用语（"立即""24小时内""账户将被冻结""urgent"）；金钱与转账（"汇款""更换收款账户""发票"）；凭证索取（"验证密码""重新登录"）；HTML 表单；隐藏文本 |
| 附件 | 危险扩展名（.exe .scr .js .vbs .iso .lnk .html .htm）；双扩展名；带宏的 Office 文档；加密压缩包，密码写在正文中 |

### 7.3 规则引擎
- 规则用 YAML 描述，热加载，便于运营调整而不用发版：

```yaml
- id: URL_TEXT_MISMATCH
  name: 链接显示地址与实际地址不一致
  category: url
  weight: 25
  condition: any_url(text_domain != href_domain and text_domain is not null)
  evidence: "显示 {text_domain}，实际跳转 {href_domain}"
```

- 规则分 `R = min(100, Σ weight)`；带 `critical: true` 的规则（如 DMARC 失败且发件域仿冒客户自有域名）命中后直接判为 `phishing`。
- MVP 目标规则数：30 条左右，覆盖 7.2 中各类特征。

### 7.4 模型

| 模型 | 输入 | 用途 |
|---|---|---|
| Baseline：TF-IDF（词 + 字符 n-gram）+ 逻辑回归 | 主题 + 正文 | 毕设对比基线；SHAP 解释；推理 < 5ms |
| Transformer：`distilbert-base-multilingual-cased` 微调，导出 ONNX | 主题 + 正文前 512 token | 主力语义模型；支持中英文 |
| 融合特征模型（毕设创新点）：Transformer 句向量 + 7.2 结构化特征 → LightGBM 或 MLP | | 实验阶段，效果确认后再上线 |

### 7.5 融合打分

```
r = 0.9 × R/100                         规则分折算为规则层置信度
S = 100 × (1 − (1 − P) × (1 − r))       noisy-OR，P = max(Pb, Pt)
任一 critical 规则命中 → S = max(S, 90)
命中白名单（发件人或域名） → S = S − 20（认证失败时不扣分）
```
- 最初设计为加权平均 S = 100 × (0.4·R/100 + 0.6·P)。实验 4 发现规则未命中时模型 70% 的把握只能得到 42 分，永远达不到"可疑"阈值，相当于给模型判断打了折扣；改为 noisy-OR 后，规则未命中时 S 等于模型概率，规则命中只会增加风险。见 `docs/实验记录.md` 实验 4。
- 阈值在验证集上确定，目标为**误报率 ≤ 1% 前提下召回率最大化**。商业产品中误报的代价比漏报更容易导致客户流失。

### 7.6 数据集与授权

| 数据集 | 用途 | 授权注意 |
|---|---|---|
| Kaggle Phishing Email Dataset（约 8.2 万封，合并 Enron、CEAS、Nazario 等） | 训练 / 实验 | 研究用途；各子集授权不同 |
| zefang-liu/phishing-email-dataset（Hugging Face） | 训练 / 实验 | LGPL-3.0 |
| Nazario 钓鱼语料、SpamAssassin | 补充 | 研究用途 |
| MeAJOR Corpus（2025） | 评测 | 查看论文中的授权说明 |
| 自建中文样本：试用客户反馈 + 人工构造 + 大模型合成 | 中文能力 | 自有，可商用；客户数据须取得书面授权并脱敏 |

> **商用前必须完成**：用自有数据或明确允许商用的数据重新训练生产模型；记录每个模型版本的训练数据来源。毕设实验可以使用研究授权的数据集。

### 7.7 评估指标
- 离线：Accuracy、Precision、Recall、F1、ROC-AUC、PR-AUC、FPR@固定召回率、单封推理耗时（CPU）。
- 鲁棒性：在大模型改写的钓鱼邮件测试集上评估性能下降幅度。
- 线上：误报率（放行数 / 隔离数）、反馈漏报数、平均处置时延（收信到隔离的秒数）。
- **MVP 上线门槛**：离线测试集 F1 ≥ 0.95，FPR ≤ 1%；单封检测 P95 耗时 ≤ 300ms。

## 9. 安全设计

| 风险 | 措施 |
|---|---|
| 客户邮箱授权码泄露 | Fernet 加密存储，密钥只存在环境变量中；接口不回传明文；日志脱敏；worker 解密后只在内存中使用 |
| 邮件内容泄露 | 只存正文摘要；原始邮件仅保存被隔离的，按保留期自动清理；数据卷建议做磁盘加密 |
| 越权 | JWT + RBAC，每个路由声明所需角色；预留 tenant_id 并在查询层统一过滤 |
| 暴力破解 | 登录失败锁定；接口限流（Redis 计数） |
| 恶意附件和链接 | 系统**从不打开链接、不执行附件**，只做静态分析；工作台中 URL 一律以纯文本展示，不渲染为可点击链接；邮件 HTML 不在前端直接渲染，只展示净化后的纯文本 |
| 误操作 | 删除需二次确认；所有处置动作写审计日志 |
| 供应链 | 依赖锁定版本；镜像基于官方 slim 镜像；定期 `pip-audit` / `npm audit` |
| 合规 | 部署文档中说明数据存储位置；提供数据导出和删除接口；与客户签订数据处理协议 |

## 11. 开发规范
- **分支**：`main` 保持可部署；功能在 `feat/*` 分支开发，合并前通过 CI。
- **提交信息**：`feat: ...` / `fix: ...` / `docs: ...`（Conventional Commits）。
- **后端**：ruff（lint + format）、mypy、pytest；接口必须有 Pydantic schema。
- **前端**：ESLint + Prettier，TypeScript 严格模式；颜色、间距、圆角一律使用 CSS 变量，不写死色值。
- **检测引擎**：每条规则必须附带至少一个命中样例和一个不命中样例的单元测试。
- **CI（GitHub Actions）**：lint → 单测 → 构建镜像。
